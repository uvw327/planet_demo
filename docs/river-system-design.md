## 0. 一句话

把"河流"从**一个生物群系**升级为**一层水文覆盖物**：

> 由降水量产流 → 顺重力下坡（填平洼地 → 多流向坡度分配）→ 按流量累积成**树枝状水系** →
> 渲染成**有宽度的河道线**（沿格间走线，不填满格子），并顺带产出**湖泊**与**内流盆地/盐湖**。

## 1. 你提的四条意见 → 四个设计结论

| 你的意见 | 设计结论 | 落在哪一节 |
| --- | --- | --- |
| 「河流不是单独的地形图块，它和山脉一样属于某种**覆盖层/覆盖物**」 | 建立**分层地表模型**：底层＝气候群系（逐格纯色），覆盖层＝地形与水文。`BIOME.RIVER` **从群系表里删除** | §3 |
| 「河流的**粗细受降雨量**影响」 | 产流量取 `moisture`（降水代用），河宽 `∝ 汇水量^0.42`。**不是"每格算 1"** —— 沙漠里的河天然细，且只有上游湿润区汇来的"过境河" | §4.2 / §4.6 / §5.3 |
| 「河流有**流向**，从山脉脚下流到别处，有的**入海**」 | 引入重力四件套：**填平洼地 → 流向 → 汇水累积 → 阈值提取**。河流源头必然落在局部高点（阶段 D 之后就是**山脊**），河口落在陆海共享边 | §4.3–§4.6 / §5.6 |
| 「渲染**绝不能是填满格子的色块**，要**树枝状水系**」 | 河网是**独立的一层几何体**：沿"格间走线"连成折线，按流量展开成**有宽度的三角带**（1 个 Mesh、1 次 draw call）。底层格子照旧显示"这里本来是什么群系" | §5 |

## 2. 为什么现在摊开做（而不是改几行 `isRiver`）

评审文档 §3 P0-2 已经写死了数学根因：

> 任何"标量场 < 阈值"的判据在球面上都是一组**闭合等值线**，闭合性来自拓扑，与参数无关。
> 所以这个问题**不可能靠调 `riverWidth` 解决**。

现在的河网就是这么来的：`isRiver()` 判 `|noise3d| < riverWidth`。后果在 §1.4 里是硬的数字：
**126 个闭环、147 个连通分量、最大水系只有 44 格、孤立河点 13.0%、断头河 31.9%、河流平均海拔只比低地低 0.021**。

而"河流粗细受降雨量影响""河流从山脉脚下流出"这两条**在现有架构里没有容身之处**：

- 没有 `downslope` → 无从谈"流向"；
- 没有汇水累积 → 无从谈"粗细"；
- 河流是 `classifyBiome()` 的一个 `return` → 占**一个格子、一个颜色**，**注定是一格一格的色块**。

所以这不是"修河流"，是**补一层缺席的模型**。按 §1 的四个结论，它同时是 P0-2 与 P1-1 的正解。

## 3. 分层地表模型（架构地基）

### 3.1 语义分层：气候 vs 地形水文

你指出的本质是：**"温带森林"和"河流"不是同一类东西。**

- 「温带森林/沙漠/草原」= **气候**决定的**原生地表覆盖**，与地形无关；
- 「山脉/雪线/河流/湖泊」= **地形与水文**决定的东西，与气候**正交**（赤道有雪峰、沙漠里有湖、雨林里有山）。

所以地表分类拆成两层：

| 层 | 语义 | 由什么决定 | 举例 |
| --- | --- | --- | --- |
| **底层（base）** | 气候群系 | 温度 + 湿度 | 雨林 / 森林 / 草原 / 沙漠 / 针叶林 / 苔原 / 冰原 / 海洋 / 海冰 |
| **覆盖层（overlay）** | 地形与水文 | 海拔 + 水 | 山脉带 / 雪线 / 河流 / 湖泊 / 内流盆地 / 盐湖 |

**河底下显示什么？** 显示底层气候群系。撒哈拉里的尼罗河，河底下就是沙漠黄 —— 这正是"覆盖物"该有的行为。

### 3.2 实现手段：面 → 顶点色，线 → 几何体

分层是**语义**，实现不必都新建几何体。规则只有一条：

| 覆盖物的形状 | 实现手段 | draw call 成本 |
| --- | --- | --- |
| **面**（湖面、山带、雪线、盐湖） | 直接改**底层顶点色**（复用现有 `repaintTile`） | **0** |
| **线**（河流、可选：山脊线、海岸线、等深线） | **独立几何体**（`LineSegments` 不够用，见 §5.1，用三角带） | **+1 层各 1 次** |
| **符号**（矿石、选中描边） | 已有：`InstancedMesh` / 全局复用 `LineLoop` | 已有 |

为什么"线"不能走顶点色：顶点色是**逐格填满**的，一条穿过格子中间、粗 1/4 格的河，顶点色画不出来。
为什么"面"不该新建几何体：新建一层要重复一整份 71682 顶点的扇形几何，纯粹浪费，而顶点色本来就够用。

**这条规则同时解释了你的直觉和 draw call 预算**：湖是面 → 0 成本；河是线 → 必须 +1 层，但仍与图块数无关。

### 3.3 层级顺序（z-order / 优先级）

```
L0 气候变化群系（顶点色，逐格纯色）
L1 湖面 / 内流湖 / 盐湖（顶点色覆盖 L0）
L2 山脉带 / 雪线（顶点色覆盖 L0）
L3 河网（独立几何体，半径 +0.002 浮在球面之上）
L4 标记层（矿石 InstancedMesh、选中描边 LineLoop）
```

L1 与 L2 极少重叠（湖在谷底、山在脊线）；若真重叠（高山冰川湖），**L1 胜** —— 水盖住岩。
L1/L2 谁覆盖谁用**判定顺序**实现（不需要真的分两个 pass，都写进 `computeTileColor` 的一个函数里）。

### 3.4 连带要改的地方（清单）

| 位置 | 改什么 | 为什么 |
| --- | --- | --- |
| `BIOME` 表 | **删除 `RIVER`** | 河流不再是群系；空出的名额留给真正的群系（稀树草原/湿地/盐湖）→ 服务 M19（≥15 种） |
| `BIOME_COLOR` / `BIOME_LABEL` | 删 `RIVER` 条目 | 同上 |

| `recomputeTerrain()` | 在 `computeClimate` **之后**插入 `computeHydrology(tiles)` | 水文需要 `elevation` + `moisture` + `temperature` 三者 |
| 图例 `buildLegend()` | 分两组显示：「气候群系」+「覆盖层（河/湖/山）」 | 语义分层的 UI 体现 |

## 4. 水文算法（数据层）

> 全部是**纯计算、一次性**跑在 `recomputeTerrain()` 里，运行时不重算。
> 复杂度 `O(n log n)`，10242 格实测应在**几毫秒**量级。**不进渲染循环。**

### 4.0 流水线总览

```
   elevation / moisture / temperature
        │
        ├─(1)─ 产流 runoff[x]                    ← 降水 − 蒸发（简化）
        │
        ├─(2)─ 填平洼地 filled[x]                ← Priority-Flood + ε（种子 = 海洋）
        │
        ├─(3)─ 流向权重 w[x][k]                  ← 多流向（MFD，按坡度幂分配）
        │
        ├─(4)─ 汇水累积 accum[x]                 ← 高→低 拓扑序，按 w 分流
        │
        ├─(5)─ 河网提取 isRiver[x] = accum > 阈值
        │
        ├─(6)─ 湖泊：filled > elevation 的连通分量 → lakeId[x]
        │
        └─(7)─ 内流盆地：湖面水量平衡 → isEndorheic[lake]（+ 盐湖）
```

### 4.1 输入

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `tile.elevation` | `computeElevations()`（地形地基后已定） | 重力、填平、湖泊水面 |
| `tile.moisture` | `computeClimate()`（阶段 A 后已定） | **产流权重**（= 降水代用） |
| `tile.temperature` | `computeClimate()` | 产流（太冷不产流）、潜在蒸发 |
| 邻接表 `adj[x]` | **新增**，从几何体反向建（"共享 ≥2 个对偶顶点"判据） | 网格拓扑 |
| 球面邻居距离 | 单位球上六边形网格，邻居间距一致（五边形略异，忽略） | 坡度 |

邻接表本来就是各验证脚本自己临时建的（`shot-v1.mjs` / `lab-terrain.mjs` / `verify-terrain.mjs` 各建一份）。
**这次把它提到 `index.html` 里，作为水文与后续所有相邻关系计算的公共输入**。规模：10242 点、**30720 条边**
（校验：`Σdeg = 12×5 + 10230×6 = 61440 = 2E` ✓，与自测里"三角形 61440"同一个数）。

### 4.2 产流 `runoff`（**河宽受降雨量影响就落在这里**）

```js
// 降水量：直接用现成的湿度场（阶段 A 已经把它修成了干净的东西）
// 冷到雪线以上不产流（先简化成 0；将来说"融雪"再加相位）
const coldFactor = clamp01((temp - tempIce) / (tempTundra - tempIce));   // 0=全冻，1=融
const runoff = Math.pow(clamp01(tile.moisture), CONFIG.hydro.runoffExponent) * coldFactor;
```

- `runoffExponent ≈ 1.5`：把"干湿差"再拉开一点。沙漠 `moisture≈0.05` → `runoff≈0.011`；雨林 `0.85` → `0.78`。
  差 **70 倍** → 河宽差 `70^0.42 ≈ 6 倍`。
- **这一行就是"河流粗细受降雨量影响"的全部秘密**：汇水量是"上游所有格子的降水之和"，
  而不是"上游格子个数"。

### 4.3 填平洼地：Priority-Flood + ε

噪声地形必然有无数局部洼地。若不填平，下坡走几步就掉进坑里 → 河网碎成 147 段（现状）。

```js
function priorityFlood(tiles, adj) {
  const n = tiles.length;
  const filled = new Float32Array(n);
  const visited = new Uint8Array(n);
  const heap = new MinHeap();                       // key = filled
  // 种子：所有水域（海洋 + 海冰 —— 即 elevation ≤ seaLevel）
  for (const t of tiles) if (t.elevation <= CONFIG.seaLevel) {
    visited[t.index] = 1; filled[t.index] = t.elevation;
    heap.push(t.index, t.elevation);
  }
  // 像"注水"一样从外向内推进
  while (heap.size) {
    const c = heap.pop();
    for (const k of adj[c]) {
      if (visited[k]) continue;
      visited[k] = 1;
      filled[k] = Math.max(tiles[k].elevation, filled[c] + CONFIG.hydro.fillEpsilon);
      heap.push(k, filled[k]);
    }
  }
  return filled;
}
```

- **球面上没有"地图边缘"**，所以用全部水域做种子就能覆盖整个星球。这是球面网格的红利。
- `fillEpsilon ≈ 1e-4`：每步强行抬升一点点，保证 `filled` 上**除真盆地外处处有严格下坡**，排除"平地打转"。
  ε 太大 → 地形被抹平、河道走位失真；太小 → 浮点误差造环。默认 `1e-4`，**列为可调参数**。
- 复杂度：二叉堆 `O(n log n)`；若将来卡顿，可换 Barnes 2014 的"两队列"变体做到 `O(n)`。
- 顺带产出：`depth[x] = filled[x] − elevation[x]` **就是"湖深"**，正数即被淹格 → 湖泊（§4.6）。

### 4.4 流向：**多流向**（MFD，按坡度幂分配）

**为什么不能用"指一个最低邻居"（D6/D8）**：六边形网格上 D6 会让河道出现**长的直线平行段** ——
这是地形水文里的经典 artifact（"noised-D8"效应），肉眼看就是"假"。

```js
function flowWeights(tiles, adj, filled) {
  const w = new Array(tiles.length);
  for (const t of tiles) {
    const x = t.index, downs = [];
    let sum = 0;
    for (const k of adj[x]) {
      const d = filled[x] - filled[k];
      if (d <= 0) continue;                          // 只往更低处
      const s = Math.pow(d, CONFIG.hydro.flowExponent);  // 坡度幂：放大最陡者
      downs.push([k, s]); sum += s;
    }
    const m = new Map();
    if (sum > 0) for (const [k, s] of downs) m.set(k, s / sum);
    w[x] = m;                                        // 分流比例，Σ = 1
  }
  return w;
}
```

- `flowExponent ≈ 1.1`：`1` = 按坡度线性分（最平滑），越大越接近 D6（越"直线"）。1.1 是"仍有分叉但收敛成主河道"的常用值。
- 五边形格只有 5 个邻居，无需特殊处理（公式与度数无关）。

### 4.5 汇水累积（拓扑序）

```js
function accumulate(tiles, filled, w) {
  const n = tiles.length;
  const accum = new Float32Array(n);
  for (const t of tiles) accum[t.index] = runoff(t);          // ★ 初始值 = 本格产流，不是 1
  // filled 严格递减于下游 ⇒ 按 filled 降序即天然拓扑序（下游必在后面）
  const order = [...tiles].sort((a, b) => filled[b.index] - filled[a.index]);
  for (const t of order) {
    const x = t.index, ax = accum[x];
    for (const [k, p] of w[x]) accum[k] += ax * p;
  }
  return accum;
}
```

**两个可以直接写进自测的定理**（§8.4）：

1. **守恒**：Σ(所有格的 `runoff`) + 0 = Σ(所有海洋格收到的入流)。全部水量最终入海（或入内流盆地，§4.7）。
2. **单调**：若 `accum[x] > T` 且 x 的主下游为非海洋格 y，则 `accum[y] ≥ accum[x] > T`。
   **推论（很漂亮）**：**"孤立河点"（度 0）在构造上必然为 0** ——
   现基线是 13.0%，M15 目标是 ≤2%，新模型是**0，且不需要任何后处理**。

### 4.6 河网提取

```js
// 阈值用"等效格数"表达，与气候解耦：把 accum 除以陆地平均产流
const unit = meanRunoffOverLand;                          // 一格"平均湿地"贡献的水量
isRiver[x] = accum[x] > CONFIG.hydro.riverCellThreshold * unit;   // 默认 20
```

- `riverCellThreshold: 20` → **直接满足** P0-2 验收里的"河流格的汇水面积中位数 ≥ 20 格"。
- 因为产流按降水加权，**河网密度天然是"湿处密、干处疏"**：沙漠里只有上游湿润区汇来的过境河。
- 预估规模：约 **12%–20% 的陆地格**落在河网里（≈470–780 格）→ 最大水系可达 200–300 格，
  对上 M14（现在 44，目标 ≥200）。

### 4.7 湖泊：`filled > elevation` 的连通分量

```js
const lakeId = labelComponents(     // 连通分量，不是湖泊格 = -1
  tiles.filter(t => filled[t.index] > t.elevation + 1e-6), adj);
```

每个分量 = **一个湖**，附带：

| 字段 | 算法 | 用途 |
| --- | --- | --- |
| `area` | 分量格数 | 过滤（`minLakeArea`）、M17 |
| `depth` | `filled − elevation` 的均值/最大值 | 颜色分档（浅湖/深湖） |
| `spillLevel` | 分量内 `filled` 的最大值 | 溢出点高程 |
| `inflow` | 从湖外流入的 `accum` 之和 + 湖面自身降水 | 水量平衡 |
| `outlet` | 下游落在湖外的那个格（= 溢出点所在格） | 出湖河 |

**坑（必须处理）**：`priority-flood` 会把**所有**洼地都填平，于是"每个湖都有一个溢出点、
每个湖最终都能流到海"。**在球面上这是数学必然**（只要填平，就没有真正的死水）。所以：
**光靠填平，永远得不到内流盆地（M18 会恒等于 0）。** 下一节才是 P1-1 的正解。

### 4.8 内流盆地与盐湖：**湖面水量平衡**（★ 这一步才是"内流"的正解）

真实的里海、咸海、大盐湖、塔里木，**不是因为拓扑封闭，而是因为蒸发 ≥ 补给**：

> 湖面会一直上升，直到"溢出"或"蒸发量追平汇水量"。
> **若在水位到达溢出点之前，蒸发就追平了汇水 → 水面停在溢出点以下 → 内流湖（盐湖）。**
> **若汇水太猛、湖面顶到溢出点 → 外流湖，多余的水从溢出点流走，形成出湖河。**

```js
// 每个湖：按格子的 elevation 做"逐步注水"
// evaporation(level) ∝ Σ_{elevation ≤ level} potentialEvap(tile)
// 解 inflow == evaporation(level) → 平衡水位 level*
for (const lake of lakes) {
  if (lake.inflow >= evapAt(lake, lake.spillLevel)) {
    lake.level = lake.spillLevel;          // 外流湖：顶到溢出点，出水 → outlet
    lake.outflow = lake.inflow - evapAt(lake, lake.spillLevel);
    lake.isEndorheic = false;
  } else {
    lake.level = solveLevel(lake, lake.inflow);   // 内流湖：蒸发追平，水位低于溢出点
    lake.outflow = 0;
    lake.isEndorheic = true;
  }
}
// 潜在蒸发：干热最强，湿冷最弱（简化）
function potentialEvap(t) { return CONFIG.hydro.potentialEvaporation * clamp01(t.temperature) * (1 - clamp01(t.moisture)); }
```

- **`potentialEvaporation` 就是内流盆地数量的唯一旋钮**：调大 → 内流变多（M18 目标 5–25）；调小 → 全是外流湖。
  这让 M18 变成**可扫参命中的指标**，而不是"看运气"。
- 内流湖的水面按 `level*` 重算面积（不是整个洼地），所以"湖的大小"也会随气候变化 —— **这正是真湖的行为**。
- 盐湖：`isEndorheic && depth 浅 && 温度高` → 单独颜色（"水面干了"的盐碱色）。

### 4.9 复杂度与耗时预算

| 步骤 | 复杂度 | 10242 格预估 |
| --- | --- | --- |
| 邻接表 | `O(E)` | < 1 ms |
| Priority-Flood | `O(n log n)` | 1–3 ms |
| 流向权重 | `O(E)` | < 1 ms |
| 汇水累积（含排序） | `O(n log n)` | 1–2 ms |
| 湖泊连通分量 | `O(n)` | < 1 ms |
| 湖面水量平衡 | `O(Σ湖格 log)` | < 1 ms |
| **合计** | — | **≈ 5–10 ms** |

调参时每次 `refresh()` 多花 10 ms，**完全可接受**。运行时不重算。

### 4.10 伪代码总装

```js
function computeHydrology(tiles) {
  const adj = buildAdjacency(tiles);                       // 提为公共设施
  const filled = priorityFlood(tiles, adj);
  const w      = flowWeights(tiles, adj, filled);
  const accum  = accumulate(tiles, filled, w);
  const unit   = meanRunoffOverLand(tiles);
  const rivers = extractRivers(accum, unit, CONFIG.hydro.riverCellThreshold);
  const lakes  = findLakes(tiles, adj, filled, accum);     // 含水量平衡 → 内流判定
  world.hydro = { adj, filled, w, accum, rivers, lakes,
                  down: mainDownstream(w),   // 渲染用的单一下游（argmax 权重）
                  through: rivers,           // 玩法接口：河是否穿过该格
                };
  return world.hydro;
}
```

## 5. 河网渲染（渲染层）

### 5.1 为什么必须用**三角带**，不能用 `Line`

| 方案 | 结论 |
| --- | --- |
| `THREE.Line` + `lineWidth` | ❌ **大多数 WebGL 平台把 `lineWidth` 钳死为 1px**（ANGLE/D3D 后端尤其）。河流要"粗细随流量"，这条直接否掉。 |
| `LineSegments` + 位移 | ❌ 只能做到"等宽 1px"，宽不起来。 |
| **三角带（quad strip）** | ✅ 每段河画成一个四边形，宽度自己算，仍只是 **1 个 Mesh、1 次 draw call**。 |

### 5.2 走线：河**穿过**格子，不填满格子

- **节点**：每段河道取"两格之间那条共享边的中点"作为转折点，与格心、抖动点交错 → 折线。
- 相邻两格的共享边中点，对双方是**同一个点** → 折线天然首尾相接，不会断开。
- **汇流处**（一个格有 2 条上游河）：从每条上游边的中点，各引一条短线接到"汇流点"（默认取该格格心）→ 天然的 **Y 形分叉**。
- **河源**：没有上游河的格，从**格心**起笔（视觉上"泉水在格内冒出"）。
- **河口**：最后一段画到**陆海共享边的中点**为止（可选再向海里延伸 0.3 格，做"入海口"）。

**每格只画"线"，底层格子照旧显示它本来的群系色** —— 这就是"覆盖物"在渲染上的落地。

### 5.3 宽度：`width ∝ 流量^0.42`，且沿程单调不回头

```js
width(x) = clamp(riverMinWidth, riverWidthScale * Math.pow(accum[x], 0.42), riverMaxWidth);
```

- `0.42` 是水力几何里"河宽 ∝ 流量^0.4~0.5"的常用指数（面积律）。
- `riverMaxWidth`（如 0.55 格）：防止主干宽过格子变成"蓝绸带"。若超上限，可改画"双线河道"符号。
- 因为 `accum` 沿下游单调不减（§4.5 定理 2），**河宽沿程自动单调不缩** —— 不需要后处理。
- 宽度在节点处按相邻段取最大值插值，避免下游突然变窄。
- **可选**：`CONFIG.hydro.climateCoupling ∈ [0,1]`，`width = (1−k)·等宽 + k·按流量`。
  `k=0` 会让你立刻看到"每格产流相同"的对照效果，用来证明"粗细确实受降雨量影响"（验收要出这张对比图）。

### 5.4 球面展开与极点

- 宽度方向 = `normalize(cross(河道切向, 球面法线))`，即**沿球面切平面**向两侧偏移。
  绝不能用固定平面坐标偏移（极点附近会被拉花）。
- 每个节点记 `r = 1 + CONFIG.hydro.riverLift`（默认 `0.002`）：抬离球面 0.2%，
  既避开与底层的 z-fighting，又肉眼不可见。
- ⚠️ 若将来打开 `enableHeightOffset`（地形起伏），`riverLift` 必须改成"跟随该格的半径"，
  否则河会钻进山里。**在设计里预留，但本次不做。**

### 5.5 打散"格网指纹"（让河看起来不像格子边）

只走"格心 / 边中点"的话，折线的转角会被六边形网格**量化到 0°/60°/120°**，
远看就是" hexagonal 折线" —— 这是 §5 里"绝不能像格子"的最后一个漏。

两道处理，**都是确定性的（同种子同结果）**：

1. **节点抖动**：格心节点沿切平面偏移一个小矢量，幅度 `nodeJitter ≈ 0.15 格`，
   方向由 `hash3(tile.index)` 决定（不引入新噪声场，纯确定性）。
   共享边中点也可沿该边滑动 ±20%。
2. **折线平滑**：对折线做 1–2 次 **Chaikin 切角法**细分 → 得到连续弯曲的河道。
   1800 段 → 7200 段，顶点数仍微不足道。

### 5.6 汇流处与河口（视觉）

| 情形 | 画法 |
| --- | --- |
| 河源 | 从格心起笔，宽度从 `riverMinWidth` 渐变到常规宽度（视觉上"细出头"） |
| 汇流 Y | 两条上游线各画到汇流点，宽度各自按上游流量 → 天然"越汇越粗" |
| 河口 | 画到陆海共享边中点，可选加宽收尾成小三角（"河口"） |
| 湖泊 | 湖面走**顶点色**（§3.2），河线在湖边**断开**（湖是一段水面，不是一条线） |
| 内流河 | 河线终止于内流湖的湖面，**不入海**（盐湖色收尾） |

### 5.7 湖泊的渲染

- 湖面 = **底层顶点色**（`L1`），成本 0。颜色按 `depth` 分档：浅湖 / 深湖 / 盐湖。
- 湖岸线可选（线型覆盖层，+1 draw call）—— 默认**不做**，先看图再决定。
- 验收要出的图：湖泊清单图（按 `area` 排序，标注内流/外流）。

### 5.8 顶点/三角形预算

| 项 | 预估 |
| --- | --- |
| 河段数 | ≈ 480–800（≈ 12%–20% 陆地格） |
| Chaikin 细分后 | ×2~×4 → ≈ 2000–3000 段 |
| 顶点 | 每段 4 个（不共享，见图）→ **≈ 1.2 万** |
| 三角形 | 每段 2 个 → **≈ 6000** |
| 对比：星球主体 | 顶点 71682 / 三角形 61440 |

**河网层是主体几何的 1/6，1 次 draw call。** 完全在预算内。

> 小技巧（可选）：把所有河段**按宽度降序**写进几何体，于是"拉远只显示主干"只需
> `geometry.setDrawRange(0, k)` —— **LOD 零重建成本**。默认不做，但接口留好。

| 不变量 | 为什么必然成立 |
| --- | --- |

| 水量守恒 | 累积是"只分发、不增减"（除非在内流湖蒸发终止） |

## 10. 已知风险与取舍（如实记录）

### 10.1 湖泊数量会"要么太多要么没有"

噪声地形里**每一个小坑**都会被 Priority-Flood 填出来，可能一次性冒出**几百个 1–3 格的小水洼**。
M17 要"湖泊 ≥30、最大湖 ≥15 格"，所以必须有 `minLakeArea` / `minLakeDepth` 过滤，
把小水洼**当成河流的过水段**（不画成湖）。这是**必须靠 H4 的标定**才能落进区间的，不能预设好看。

### 10.2 `fillEpsilon` 是"隐形的总开关"

它同时影响：河道的走位（ε 大 → 河走"填平的平面" → 失真）、湖泊的数量（ε 大 → 更多格被认为"被淹"）、
以及"会不会出现环"。**它是本次最容易调出诡异结果的一个参数**，所以我会在 lab 里把它单独扫一遍。

### 10.3 河网几何体**必须重建**（打破了"调参不重建几何体"的便利）

地形地基阶段建立了一个很舒服的性质：改 `CONFIG` 后 `refresh()` 就能看新结果，**不重建几何体**
（因为海拔不参与顶点坐标）。但**河网是几何体**，`riverCellThreshold` 一改，河段集合就变了。

处理方式：`refresh()` 里在必要时调用 `rebuildRivers()`（重建河网几何体）。
成本：约 1.2 万顶点的重建 ≈ **10–20 ms**，一次性、不在循环里。
**这是可接受的**（调参时本来就慢 10 秒也等得起），但我会在文档里标清"这一步之后，
`refresh()` 不再是零几何体成本"。**渲染层的 draw call 红线不变。**

### 10.4 MFD 的"实数流量" vs 渲染要的"单一走向"

多流向是**为算准流量**，但画线需要**一条明确的路**。做法：流量用 MFD 累积，
走向取 `argmax w[k]`（等价于"多点流向 + 单点画线"）。副作用：部分支流的流量被"借"给了主干，
分叉比（M29）可能偏高 → 用 `flowExponent` 调。

### 10.5 球面极点

极点附近的格子是**规则六边形**（Goldberg 多面体在 12 个五边形之外都是六边形，没有"经线汇聚"问题），
所以**溢出像素在极点附近不会拉花** —— 这是球面网格相对等距圆柱投影的一个真实优势。
但宽度偏移仍必须用切平面（§5.4）。

### 10.6 内流盆地是"物理模型"不是"验证过的水文模型"

§4.8 的水量平衡是**游戏地图尺度的合理简化**（单层、稳态、无地下水、无季节），
目标是让"干旱区出现盐湖、湿润区出现外流湖"这个**定性事实**成立。
不要把它当成可以预测真实流域的工具 —— 我会在文档里一直这么标注。

## 14. 一句话总结这份设计

> **河流不再是"染成蓝色的格子"，而是一层"水的走向"。**
> 水从降水来（粗细），顺重力走（流向），汇成树（树枝状），入海或入湖（终局），
> 画成线而不是色块（渲染）。而"内流盆地"要靠**湖面的蒸发平衡**才能自然长出来 ——
> 这是这套设计里唯一一个"必须多算一步"的地方，也是它区别于"随便塞个湖色"的全部价值。
